# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

C++23 gRPC service that rewrites ClickHouse SQL before it reaches a backend ClickHouse cluster. Links directly against the ClickHouse source tree (vendored as the `clickHouse/` git submodule) so it can parse queries into ClickHouse's own AST, mutate them via transformers, and format them back out.

Entry point: `src/rewriter-server.cc` — gRPC server + `main()` (guarded by `REWRITER_RELEASE_MAIN`). Invocation: `clickhousegate_rewriter [grpc_port] [http_port]`. Defaults: gRPC `50051`, HTTP `grpc_port + 1`.

The request-handling logic lives in protocol-agnostic `RewriterServiceImpl::doRewrite` and `doRewriteErrorMessage`. The gRPC `Rewrite` / `RewriteErrorMessage` methods are thin wrappers that delegate and return `Status::OK` (`RewriteErrorMessage` also hands its call's cancellation to `doRewriteErrorMessage`) — never add logic to the wrappers, always to the `do*` methods, so the HTTP façade stays in sync.

**HTTP+JSON façade**: [src/rewriter-http-server.h](src/rewriter-http-server.h) + [src/rewriter-http-server.cc](src/rewriter-http-server.cc) wrap the same `RewriterServiceImpl` instance behind a Poco::Net HTTPServer (Poco is already a transitive dep via `clickhouse_common_io`, no new linkage). Routes: `POST /rewrite`, `POST /rewriteerrormessage`, `POST /optimize`, `POST /materialize` (also accept gRPC-style `/rewriter.RewriterService/<Method>`), `GET /healthz`. Body is JSON matching the proto messages — converted via `google::protobuf::util::JsonStringToMessage` / `MessageToJsonString`. The HTTP server runs in its own Poco thread pool started from `RunServer`; the gRPC `Wait()` is what blocks main.

`src/main.cc` and `scripttest.sh` are deprecated — not wired into any build target. Don't spend time on them.

## Build / test / run

**ClickHouse does not compile on local dev machines** — all builds and tests happen on a dedicated remote build box. The local checkout is for editing; every build crosses the network.

### Remote build box

- **SSH:** `ssh rewriter-build-box`, an `~/.ssh/config` host alias. The address and port are not in this repository; maintainers get them from the internal build-box runbook (internal design doc `2026-11-06-build-box-and-release-runbook`).
- **Dev workdir (has build cache):** `~/chen/rewriter-grpc/`
- **Release CI workdir (used by `.github/workflows/release.yml`):** `~/ci/rewriter/`
- **Pull-request CI workdir (used by `.github/workflows/ci.yml`):** `~/ci/rewriter-ci/`
- Other directories like `~/chen/sql-rewriter/` or `~/limengyu/sql-rewriter/` are stale — ignore them.

### Typical dev loop

```shell
# 1. Push local edits to the dev workdir. Exclude heavy dirs so rsync is fast.
rsync -az --delete \
  --exclude='.git' --exclude='build/' --exclude='clickHouse/' \
  --exclude='contrib' --exclude='docs/' \
  ./ rewriter-build-box:chen/rewriter-grpc/

# 2. Incremental build (30s-3min).
ssh rewriter-build-box \
  "cd ~/chen/rewriter-grpc && ./scripts.sh rebuild"

# 3. Run tests.
ssh rewriter-build-box \
  "cd ~/chen/rewriter-grpc && ctest --test-dir build --output-on-failure"
```

Use `./scripts.sh build` (not `rebuild`) only when `build/` is missing or the build state looks corrupt — full build is ~15-20min. `rebuild` re-runs `cmake` configure on every invocation (~1-3s no-op when nothing changed), so `CMakeLists.txt` edits and `git describe`-derived version stamps are picked up automatically; you don't need to remember to switch commands.

### `./scripts.sh` commands

The wrapper handles symlinks and submodule patches that `ninja` otherwise trips on. Chinese comments inside.

```shell
./scripts.sh prepare          # install toolchain (apt+LLVM on Linux, brew on macOS)
./scripts.sh build            # full clean build (wipes build/, ~15-20 min)
./scripts.sh rebuild          # incremental; use this day-to-day. Falls through to build if build/ is missing.
./scripts.sh test             # build + ctest
./scripts.sh clean            # rm -rf build/
./scripts.sh docker build <v> # stages build/clickhousegate_rewriter → docker/bare/root/ then buildx
./scripts.sh docker push  <v>
```

Prerequisite submodule init on a fresh clone (run from the repository root):
`git submodule update --init --recursive --depth=1`.

Single-test runs (gtest binary):
```shell
./build/rewriter_tests --gtest_filter='CTEOnly.RunByName_Simple'
```

Under the hood `build` runs `cmake -B build -GNinja -DENABLE_RUST=OFF -DENABLE_TESTS=OFF -DBUILD_TESTING=ON -DENABLE_THINLTO=OFF -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_EXE_LINKER_FLAGS=-fuse-ld=mold` then `ninja -C build clickhousegate_rewriter rewriter_tests`. The main target name is `clickhousegate_rewriter`; tests are `rewriter_tests`.

### Cutting a release

Don't bump versions by hand. Use the `cut-release` workflow (`Actions → cut-release → Run workflow`). It tags `main` as `vX.Y.Z` in UTC — first cut of a new UTC day bumps Y (minor), subsequent cuts same day bump Z (patch) — then dispatches `release.yml` which builds + pushes the docker image on the build host.

### Submodule brittleness (important)

`scripts.sh`'s `build` runs `git submodule foreach --recursive 'git reset --hard && git clean -fdx'` at the end, which also wipes the `clickHouse/src/clickHouse` self-symlink needed for `#include "clickHouse/..."` to resolve, and reverts in-tree patches. Both `build` and `rebuild` call `ensure_symlinks` + `ensure_patches` on entry to re-establish them:

- `clickHouse/src/clickHouse -> .` and `./contrib -> clickHouse/contrib`
- `flatbuffers/include/flatbuffers/stl_emulation.h`: drop `const` from `size_type count_`
- `numactl-cmake/CMakeLists.txt`: append `distance.c / affinity.c / sysfs.c / rtnetlink.c` so the static lib exports `resolve_affinity` etc.

If you touch the build by hand (not via `scripts.sh`), apply the same symlinks/patches or ninja will fail with "file not found" on `Dictionaries/DictionaryFactory.h` or `undefined symbol: resolve_affinity`.

## Architecture

### Request flow

`RewriterService.Rewrite` in [src/rewriter-server.cc](src/rewriter-server.cc):

Before parsing, the server resolves the effective last-wins `TableNameRewrite` selection. An effective dynamic option activates the storage-integrity surface when it carries `STORAGE_INTEGRITY_CONTRACT_V2` (even with an empty `storage_integrity.tables` map) or has a non-empty `tables` map, and an active option must carry V1 or V2; every table entry, logical key, read-mode enum, physical name, and reserved row-id identifier is validated before the response acknowledges the received version. Once accepted, the acknowledgement is present on every parse and dispatch outcome. Shadowed SI options and V1 options with an empty table map do not activate the contract. V2 differs from V1 in that activation, in protecting every `storage_integrity.reserved_databases` entry exactly like a database named by a safe/unsafe table (V1 ignores the field), and in accepting a plain `DROP TABLE [IF EXISTS] name[, name...] [SYNC]` of logical SI tables, each of which drops only its ordinary physical table.

1. **No IN preprocessing** — the SQL is parsed as written. A regex `QueryPreprocessor` used to split `IN` lists of more than 50 elements into OR batches as a parser stack guard; under `parseBounded` a 100,000-element list is one flat tuple a few levels deep, and the split changed meaning (`abs(x) IN (…)` became `abs((x) IN (…) OR …)`), refused NOT IN / GLOBAL IN and rewrote string literals, so it was removed (rewriter-go never split). `tests/large_in_list_test.cc` pins the large-list shapes.
2. **Parse** — `parseBounded` ([handlers/common.h](src/handlers/common.h)) runs `DB::parseQuery(DB::ParserQuery, ...)` within ClickHouse's own default bounds (`max_parser_depth` / `max_parser_backtracks` / `max_ast_depth`; see **Resource bounds** below) and produces an `ASTPtr`. Parse errors return `RewriteCode::SyntaxError` with `Status::OK` (never a gRPC error). `registerFieldOnlyChildren` ([handlers/common.h](src/handlers/common.h)) then adopts the AST members ClickHouse keeps outside `children` (see **Table-reference policy** below).
   - **Table-reference preflight (dynamic mode, housegate spec 2026-09-26)** — `preflightTableReferences` in [handlers/table_reference.cc](src/handlers/table_reference.cc) runs before any handler can rewrite a name; static and no-rewrite requests pass untouched. Its steps, in the cross-engine precedence order (the first that fires answers):
     1. **Lambda reads.** A lambda (an `APPLY(x -> …)` transformer's or any higher-order function's) whose body holds a subquery (EXISTS included), an operator-form IN / NOT IN / GLOBAL IN over any operand, or an IN-family call whose operand is a table identifier (`in(x, t)`) is `UnsupportedStatement` `statement is not supported` (the SI catch-all text while the surface is active).
     2. **T2.** An `{p:Identifier}` in any database or table position (INSERT VALUES rows and opaque INSERT text included), or anywhere in an unmodelled class, is `InvalidRewriteRequest` `query parameters are not supported in a database or table position`.
     3. **Shapes no handler can carry.** A parametrised alias (`AS {name:Identifier}`, which ClickHouse's formatter never prints) and a TimeSeries table's `SAMPLES` (`DATA`) / `TAGS` / `METRICS` / `RECENT SAMPLES` target clause (or `INNER COLUMNS` on any view target) are `statement is not supported`, and so are the ClickHouse 26.8 shapes no handler models (`unmodelledClickHouse268Shape`): a `STREAM` table expression at any depth, a `LOCAL` or `NATURAL` join (25.8 / 26.3 read a bare `local` after a table as its alias), a MergeTree `UNIQUE KEY` (a storage expression neither R2 nor the SI write path inspects), `ALTER … MODIFY SENTIO BINARY TYPE ORIGIN` (the fork's privileged one-time registration of a table's binary type origin) and `DESCRIBE TEMPORARY TABLE`.
     4. **T7.** An unmodelled statement class, `DESCRIBE (SELECT …)` and a DESCRIBE of a data-only or external table function whose arguments hold a query are `UnsupportedStatement` `statement is not supported`. With the SI surface active the SI write preflight runs first, then the SI catch-all text answers. A session `SET` is the one modelled pass-through while the surface is inactive.
     5. **T3.** A protected database — a `database_map` value, a `protected_databases` entry (each validated as a simple identifier on every dynamic request, `InvalidRewriteRequest` otherwise; the same validation refuses a `database_map` value `system`, `information_schema` or `INFORMATION_SCHEMA`, `database_map entry "<logical>" maps to the metadata database "<physical>"`, checked in key order), and while the SI surface is active any SI physical or reserved database — is `InvalidRewriteRequest` `protected database <db> is not addressable` in every read, target and carrier-argument position, the session's logical database included. While the surface is active an SI physical name defers to the SI handlers, except inside a string-lookup argument.
     6. **System tables.** A system table outside the allowlist is refused, or deferred to the SI pipeline (**System tables** below).
     7. **T5.** The table-function, table-engine (matched case-sensitively) and `disk` / `storage_policy` table-setting allowlists. A DESCRIBE target that is a table function is checked here in both SI states; the rest only while the surface is inactive.
     8. **T6.** Every joinGet / joinGetOrNull / dictGet-family call (in INSERT VALUES rows and as an `APPLY(dictGet…)` / `APPLY(joinGet…)` transformer too), and every hasColumnInTable outside a rewritten SELECT body (where it is rewritten), is `InvalidRewriteRequest` `<fn> target "<arg>" does not resolve through the caller's databases`. Both SI states.
     9. **R5.** A refused setting is a table-setting refusal and a non-literal setting value is `statement is not supported` (**Settings (R5)** below). Only while the surface is inactive.
     10. **R2.** A read in a position no rewrite reaches is `statement is not supported`: ALTER actions (`MODIFY REFRESH … DEPENDS ON` included) and header-SETTINGS INSERT text (literal-only IN rule); structured UPDATE / DELETE, column / constraint / index / projection / storage expressions, ENGINE arguments and INSERT VALUES rows (a table, table function or table-naming IN operand); REFRESH views; `FROM INFILE`; and a VALUES payload that does not parse as expression rows or carries any comment or a malformed `\x` escape (the Values reader, not the SQL lexer, executes it). Only while the surface is inactive.

     While the SI surface is active, T5, R5 and R2 run inside the SI SELECT and write paths after the SI namespace policy, so an SI-owned message wins. The SELECT path also rewrites and reports IN operands that name a table (T4) and refuses an unqualified name that does not resolve; SHOW COLUMNS / SHOW INDEX / DESCRIBE resolve an unqualified target like FROM, and every SHOW form's WHERE / LIMIT refuses reads (R7). A few refusals apply after the handlers, to a would-be Success (**After the handlers** below).
3. **Dispatch by statement kind** (handlers live under [src/handlers/](src/handlers/); each returns a disposition that either consumes the request or falls through to the next). The single `TableNameRewrite` option carries two sub-messages: `static_args` (the three-map policy: `table_map` / `remote_table_map` / `table_with_database_map`) and `dynamic_args` (dynamic construction). Every table-targeting handler — SELECT plus the non-SELECT single-target handlers (writes / EXISTS / SHOW CREATE / RENAME) — picks mode via the **unified static→dynamic precedence**: if `static_args` is set, use static-mode (even when every map is empty — that's an explicit "static-only, no rewrite" intent); otherwise fall back to `dynamic_args`. Once static-mode is selected, unmatched targets pass through unchanged (statement-level — no per-target fallback to dynamic). Database-level handlers (USE / SHOW TABLES / SHOW DATABASES / CREATE DATABASE) bypass this precedence and read `dynamic_args` directly via `findDynamicArgs`, since `static_args` is table-keyed and has no semantic meaning for a db-level operation.
   - `ASTUseQuery` → [handlers/use.cc](src/handlers/use.cc). Consumes `dynamic_args.database_map` + `dynamic_args.known_physical_databases`. `database_map` hit → `USE <physical>` + `table_rewrites` entry. Target is already a known physical DB → passthrough. Neither → `InvalidRewriteRequest` ("user does not have this database"). No option → passthrough.
   - `ASTShowTablesQuery` → [handlers/show_tables.cc](src/handlers/show_tables.cc). Consumes `dynamic_args`. Resolves `logical := FROM-clause || upstream_logical_database_in_context`, `physical := database_map[logical]` (or `logical` itself if known physical). Emits a filtered `SELECT … FROM system.tables WHERE database = '<physical>' AND startsWith(name, '<prefix>')` with `multiIf` stripping the prefix; `prefix = logical + delim + (extra_args joined by delim + delim, iff non-empty)`. When `logical` is in `dynamic_args.logical_database_to_remote_upstream_index` the `FROM system.tables` source is swapped for `FROM remote('<addr>', system, tables, '<user>', '<password>')` so the enumeration runs against the upstream cluster (filter + prefix-strip unchanged); a logical pointing at a missing `remote_upstreams` key rejects with `InvalidRewriteRequest`. Rejects with `InvalidRewriteRequest` when logical can't be resolved. In dynamic mode the synthetic SELECT models only `SHOW TABLES [{FROM | IN} <db>]`, so after the database resolves, R7 and R5, any clause it would drop — LIKE / ILIKE (an empty pattern included), WHERE, LIMIT, FORMAT, INTO OUTFILE, SETTINGS — and SHOW FULL / TEMPORARY TABLES are refused with `statement is not supported`; SHOW DICTIONARIES / MERGES / FILESYSTEM CACHES are refused as the system tables they read (`system.dictionaries` / `system.merges` / `system.filesystem_cache_settings`). No option → passthrough.
   - `ASTShowTablesQuery` with `databases == true` (= `SHOW DATABASES`) → [handlers/show_databases.cc](src/handlers/show_databases.cc). Consumes `dynamic_args`. With no `dynamic_args`: passthrough. With `dynamic_args`: emits `SELECT name FROM (<union>) [WHERE name [NOT] (I)LIKE '<pat>'] ORDER BY name`. **Only logical DBs from `database_map` are surfaced** — `known_physical_databases` is consulted as a trust anchor but its members are never emitted as result rows (multi-tenant isolation: physical DB names are an internal detail). Per-`database_map` entry, sorted alphabetically by `<logical>`: (1) skip the entry entirely when `<physical>` is not a member of `known_physical_databases` (config-drift guard — no subquery, no `database_rewrites` record); (2) otherwise emit a bare `SELECT '<logical>' AS name`. We don't existence-check tables anymore: a declared+trusted logical DB is always returned (an empty logical DB is still a valid DB the caller can write into, and remote-mapped logicals would have failed a local existence check anyway). When no entries survive the filters, the body is the zero-row sentinel `SELECT '' AS name WHERE 0`. `extra_arguments` and `delim` are ignored here — they only matter for the table-prefix construction used by SHOW TABLES. Honors `SHOW DATABASES LIKE / NOT LIKE / ILIKE`; any other clause the synthetic SELECT would drop (WHERE, LIMIT, FORMAT, INTO OUTFILE, SETTINGS) and FULL / TEMPORARY are refused with `statement is not supported`, after R5. Records the kept `database_map` entries in `response.database_rewrites`. `statement_type = STATEMENT_TYPE_SHOW_DATABASES`.
   - `ASTShowColumnsQuery` / `ASTShowIndexesQuery` (`SHOW [EXTENDED] [FULL] COLUMNS | FIELDS | INDEX | INDEXES | INDICES | KEYS {FROM | IN} …`) → `handleShowColumnsQuery` in [handlers/show_tables.cc](src/handlers/show_tables.cc). Guards SI physical and logical namespaces, runs R7 on the trailing clauses, refuses a table clause of three or more parts, maps its target like an EXISTS target in dynamic mode (an unqualified one through the session's logical database, a qualified one — `FROM db.t` or `FROM t FROM db` — through `database_map` ∪ `known_physical_databases`, an unresolvable database refused with `InvalidRewriteRequest`; spec 2026-09-26 R7, amended 2026-11-07), and otherwise — a `system` / `information_schema` target, or no dynamic args — echoes the original text (the formatter does not round-trip this family). `statement_type = STATEMENT_TYPE_SHOW_TABLES`.
   - The SHOW forms that name no table and have no handler of their own (PROCESSLIST, USERS / ROLES / PROFILES / POLICIES / QUOTAS, GRANTS, ACCESS, FUNCTIONS, ENGINES, SETTING, PRIVILEGES, SHOW CREATE of an access entity, DESCRIBE FILESYSTEM CACHE) → `handleShowSystemFormQuery` in [handlers/system_tables.cc](src/handlers/system_tables.cc), dynamic mode only; see **System tables** below.
   - `ASTExistsTableQuery` → [handlers/exists.cc](src/handlers/exists.cc). Resolves the active mode via `findActiveTableRewrite` (unified static→dynamic precedence). Static-mode: three-map lookup; unmatched → passthrough; `remote_table_map` hit → `UnsupportedStatement`. Dynamic-mode: `applyDynamicRewrite` on the target. `statement_type = STATEMENT_TYPE_EXISTS_TABLE`. `EXISTS DATABASE / VIEW / DICTIONARY` return `UnsupportedStatement`.
   - `ASTShowCreateTableQuery` → [handlers/show_create.cc](src/handlers/show_create.cc). Parallel to EXISTS; `statement_type = STATEMENT_TYPE_SHOW_CREATE_TABLE`. `SHOW CREATE DATABASE / VIEW / DICTIONARY` return `UnsupportedStatement`.
   - `ASTDescribeQuery` → [handlers/describe.cc](src/handlers/describe.cc). `DESCRIBE [TABLE]` is classified as `STATEMENT_TYPE_DESCRIBE`; an SI target becomes a `system.columns` metadata SELECT over its safe physical table with the reserved row-id column filtered out (a FORMAT / INTO OUTFILE / SETTINGS clause that SELECT would drop is refused with `statement is not supported`), while an ordinary target is mapped like an EXISTS target in dynamic mode — unqualified through the session's logical database, qualified through `database_map` ∪ `known_physical_databases`, an unresolvable database refused with `InvalidRewriteRequest` (spec 2026-09-26 R7, amended 2026-11-07) — and formatted with its clauses; a `system` / `information_schema` target is passed through. `DESCRIBE DATABASE / VIEW / DICTIONARY` is `UnsupportedStatement`, but physical SI namespace classification runs first so those rejects still carry fail-closed SI metadata.
   - `ASTGrantQuery` → [handlers/grant.cc](src/handlers/grant.cc). Dispatched **before** writes (so it never falls into the write-kind switch). Symmetric to CREATE/DROP DATABASE: the rewriter never executes the GRANT/REVOKE on ClickHouse — a logical DB shares its physical DB with sibling tenants via prefix-sharing, so a CH-level grant scoped to the physical DB would leak across tenants. With `dynamic_args` present, walks `access_rights_elements`, resolves logical → physical via `resolvePhysicalDatabase`, and emits one `PrivilegeDelta` per element into `response.privileges_deltas` (action = GRANT/REVOKE; scope = SCOPE_TABLE for `db.t`, SCOPE_DATABASE for `db.*`; privilege keywords from `AccessFlags::toKeywords()` preserved verbatim; grantees translated from the `ASTRolesOrUsersSet` with `is_current_user` set for the CURRENT_USER literal and names left otherwise un-mapped). Then drops `cluster` from the AST and rewrites the SQL to `SELECT '<original SQL minus ON CLUSTER>' AS gstmt` (or `... AS rstmt` for REVOKE) so the user's intent ends up in CH `query_log`. `statement_type = STATEMENT_TYPE_GRANT | _REVOKE`. Unsupported variants (`ON *.*`, role-membership grants — `GRANT role TO user` — detected via non-null `ASTGrantQuery::roles`, column-level grants `GRANT SELECT(c1) ON …`, `WITH REPLACE OPTION`, `REVOKE FROM ALL`/`ALL EXCEPT`, `GRANT CURRENT GRANTS`, `ATTACH GRANT`) return `UnsupportedStatement`. No `dynamic_args` → also `UnsupportedStatement` (mirrors CREATE/DROP DATABASE; we won't ship raw GRANT to the physical DB without policy context). Logical not in `database_map`/`known_physical_databases`, or bare table without `upstream_logical_database_in_context`, → `InvalidRewriteRequest`. Successful ordinary permission changes use `privileges_deltas` rather than `original_accessed_tables`; an SI table/database/physical-namespace reject does add an SI-classified accessed entry so downstream callers can fail closed.
   - `ASTCreateQuery / ASTDropQuery / ASTAlterQuery / ASTInsertQuery / ASTUpdateQuery / ASTDeleteQuery / ASTRenameQuery` → [handlers/writes.cc](src/handlers/writes.cc). Each target goes through the unified `rewriteOneTarget`: in static-mode it's a three-map lookup (unmatched → passthrough; `remote_table_map` hit → `UnsupportedStatement` since writes can't target a `remote()` function); in dynamic-mode it's `applyDynamicRewrite`. `statement_type = STATEMENT_TYPE_CREATE_TABLE | _DROP_TABLE | _TRUNCATE_TABLE | _ALTER_TABLE | _INSERT | _UPDATE | _DELETE | _RENAME_TABLE`. TRUNCATE TABLE and DROP TABLE share the unified single-target path (same `ASTDropQuery`, just `kind == Truncate`); only the response `statement_type` distinguishes them. For CREATE TABLE AS, the source table is rewritten the same way; for RENAME, every `from` and `to` element. INSERT has an extra wrinkle: `ASTInsertQuery::formatImpl` only emits the prelude (`INSERT INTO ... [columns] [SETTINGS ...] [VALUES|FORMAT <fmt>]`) — the inline payload after `VALUES` / `FORMAT <fmt>` lives off-AST as raw `data`/`end` pointers into the original SQL buffer, since ClickHouse normally streams those bytes to the executor out-of-band. The handler appends `[data, end)` verbatim to the formatted SQL so a `VALUES (1)` request round-trips as `... VALUES (1)` instead of a bare `... FORMAT Values` (which would put the upstream into "wait for wire-format data" mode and hang the client). `CREATE VIEW` / `CREATE MATERIALIZED VIEW` → `handleViewCreate` in [handlers/writes.cc](src/handlers/writes.cc): the view name and (for a materialized view) the `TO` target go through the unified single-target `rewriteOneTarget`; the body `SELECT` goes through `rewriteEmbeddedViewBody` ([handlers/select.cc](src/handlers/select.cc)), the `View` form of `rewriteEmbeddedBody` — full option pipeline plus the cross-shard GLOBAL pass; an INSERT … SELECT or CREATE TABLE … AS SELECT body goes through the same function (`EmbeddedBodyKind::InsertSelect` / `CreateSelect`). `statement_type = STATEMENT_TYPE_CREATE_VIEW | _CREATE_MATERIALIZED_VIEW`. `CREATE LIVE VIEW` / `WINDOW VIEW` / `CREATE DICTIONARY` still return `UnsupportedStatement`. `DROP VIEW` flows through the single-target `DROP TABLE` path with `statement_type = STATEMENT_TYPE_DROP_VIEW`; `TRUNCATE VIEW` / `DROP DICTIONARY` stay rejected. Unsupported variants (CREATE LIVE/WINDOW VIEW, CREATE DICTIONARY, TRUNCATE VIEW, DROP DICTIONARY, multi-table DROP/TRUNCATE, RENAME DATABASE/DICTIONARY, TRUNCATE DATABASE / TRUNCATE ALL TABLES FROM, DETACH, UNDROP, OPTIMIZE, KILL, BACKUP/RESTORE, INSERT INTO FUNCTION, `ALTER TABLE ... ATTACH/REPLACE/FETCH PARTITION FROM other`, `ALTER TABLE ... MOVE PARTITION TO TABLE other`, …) return `UnsupportedStatement`. Dynamic-mode unqualified target + empty `upstream_logical_database_in_context`, or logical that resolves to no physical DB → `InvalidRewriteRequest`. No option → passthrough.
   - `ASTCreateQuery` with no table (`CREATE DATABASE <db>`) → still in [handlers/writes.cc](src/handlers/writes.cc) but follows a special path: the rewriter never emits the DDL against ClickHouse. With `dynamic_args` present it (1) rejects `InvalidRewriteRequest` if `<db>` is already in `database_map` and the SQL is not `IF NOT EXISTS`, (2) rejects if `dynamic_args.upstream_physical_database_in_context` is set but not in `known_physical_databases`, (3) otherwise rewrites to `SELECT '<original SQL>' AS cdstmt` so the user's intent ends up in ClickHouse `query_log`. `statement_type = STATEMENT_TYPE_CREATE_DATABASE`. Without `dynamic_args`, falls back to `UnsupportedStatement` (we won't ship raw CREATE DATABASE to the physical DB).
   - `ASTDropQuery` with no table (`DROP DATABASE <db>`) → still in [handlers/writes.cc](src/handlers/writes.cc), symmetric to CREATE DATABASE: never emits the DDL against ClickHouse (a logical DB shares its physical DB with sibling tenants via prefix-sharing, so a single CH-level `DROP DATABASE` would nuke unrelated tenants). With `dynamic_args` present it (1) rejects `InvalidRewriteRequest` if `<db>` is not in `database_map` and the SQL is not `IF EXISTS` (`known_physical_databases` is deliberately not consulted — physical-DB lifecycle is out of scope), (2) on a `database_map` hit records `database_rewrites[<db>] = <physical>` so an external GC binary knows where to scan for prefixed tables, (3) rewrites to `SELECT '<original SQL>' AS ddstmt` so the intent lands in `query_log` for the GC binary to tail. `statement_type = STATEMENT_TYPE_DROP_DATABASE`. Without `dynamic_args`, falls back to `UnsupportedStatement`. Actual physical-side reclamation is the GC binary's responsibility — the rewriter is fire-and-forget here.
   - Everything else (`SELECT`, other DML) → falls through to [handlers/select.cc](src/handlers/select.cc).
4. **SELECT path** — collect `original_accessed_tables` (one `AccessedTable` per `ASTTableExpression`, carrying `original_database` / `original_table` plus the rewriter's resolved `logical_database` / `physical_database` / `is_remote`) via `collectAccessedTablePairsFromAST` in [handlers/select.cc](src/handlers/select.cc) and the per-pair `resolveAccessedTable` in [handlers/name_rewrite.cc](src/handlers/name_rewrite.cc). Both `collectAccessedTablePairsFromAST` and the dynamic-mode rewrite walker carry a `CTEAliasScope` ([handlers/cte_scope.h](src/handlers/cte_scope.h); the binding rules are under **Table-reference policy** below): a **bare** `ASTTableIdentifier` whose name is an in-scope read-query CTE, or a bare IN operand the scope binds, is skipped entirely — it is not a real table, so it neither lands in `original_accessed_tables` nor gets rewritten as `<logical>.<alias>`. Qualified `db.alias` references are still treated as real tables (the qualifier disambiguates). Externally-supplied CTE bodies (from a `CommonTableExprRewrite` option) additionally erase the alias from `originals` and re-walk the body so the real tables it accesses inline. Then iterate `request.options()` and apply transformers in option order: Limit → TableName → Offset → Settings → CTE. The TableName step follows the unified static→dynamic precedence: `static_args` set → `ASTReplaceTransformer` (three-map walk; an empty static_args means every identifier is unmatched and passes through). Otherwise falls back to walking the AST and applying `applyDynamicRewrite` from `dynamic_args` to each `ASTTableExpression` (lenient for a qualified name — one whose database resolves to nothing is left as written; in dynamic mode an unqualified name that does not resolve was already refused, see **Table-reference policy** below; inline CTE aliases are filtered out by the scope above before resolution is even attempted).
5. **Populate `table_rewrites` / `database_rewrites`** — every rewrite that fired is recorded on the response. Table-level rewrites (SELECT, writes, EXISTS, SHOW CREATE, RENAME) go into `table_rewrites` keyed by `"origin_db.origin_table"` → `"rewritten_db.rewritten_table"`. DB-level rewrites (USE, SHOW TABLES, DROP DATABASE on a `database_map` hit) go into `database_rewrites` keyed by the original logical DB → physical DB. No-op rewrites (origin == rewritten) are omitted from both maps.
6. **Cross-shard correctness pass (SELECT only)** — `forceGlobalForRemoteAsymmetry` in [handlers/select.cc](src/handlers/select.cc) walks the post-rewrite AST bottom-up. For each `ASTSelectQuery`: (a) scan `tables()` left→right and, for any `ASTTableJoin` where the accumulated-left side has a remote source (`remote` / `remoteSecure` / `cluster` / `clusterAllReplicas` table function) and the current element has a real-table local source, or vice-versa, bump `locality` from `Unspecified` to `Global`; (b) if the FROM list contains any remote source, walk the rest of the SELECT body (skipping `tables()` and `with()` and not descending into nested `ASTSubquery` — those have already been processed bottom-up) for `ASTFunction` calls named `in` / `notIn` / `nullIn` / `notNullIn` whose right operand has a local source, and rename them to `globalIn` / `globalNotIn` / etc. Symmetric remote-vs-remote and local-vs-local joins are intentionally left untouched (per request) — GLOBAL costs an extra broadcast and the symmetric cases work without it. User-written `GLOBAL` / `LOCAL` are preserved (we only override `Unspecified`). Bare CTE-alias references (in scope) don't count as local sources, so a JOIN against a CTE alias whose body references a local table is a current limitation — callers who hit this can write `GLOBAL` explicitly. The pass runs *after* option application so static-mode `remote_table_map` and dynamic-mode `logical_database_to_remote_upstream_index` rewrites that *introduce* remote() calls are visible. INSERT … SELECT, CREATE TABLE … AS SELECT (EMPTY included) and CREATE VIEW / MATERIALIZED VIEW bodies run the pass through `rewriteEmbeddedBody` ([handlers/select.cc](src/handlers/select.cc)), which also rewrites them and reports their sources after the write target (spec 2026-09-26 T4); other non-SELECT statements bypass it.
7. **Format** — `formatAst` ([handlers/common.h](src/handlers/common.h)): `ast->formatWithPossiblyHidingSensitiveData(0, one_line=true, show_secrets=true, print_pretty_type_names=false, rule=WhenNecessary, style=Backticks, ignore_redundant_parentheses=true)` produces the output SQL. Secrets are shown because the output is what the backend runs; the grouping parentheses ClickHouse 26.8 remembers (`WHERE (a = 1)`) are dropped, so the output keeps the 26.3 spelling the 25.8 / 26.3 backends were measured against.

### Resource bounds

Every bound is an environment variable read per request ([src/request_limits.h](src/request_limits.h)); names and defaults match the upstream sql-rewriter's overload protection.

- **Parse depth.** Caller SQL is parsed only through `parseBounded` ([handlers/common.h](src/handlers/common.h)): `DBMS_DEFAULT_MAX_PARSER_DEPTH` (1000), `DBMS_DEFAULT_MAX_PARSER_BACKTRACKS` and an iterative depth check (`checkPolicyAstDepth`, `kMaxAstDepth = 1000`) that also descends into the field-only members `registerFieldOnlyChildren` adopts, so every later recursion (clone, registration, the walkers) runs on a bounded tree. These are the ClickHouse server defaults, so a refused statement is one the server would refuse too. Unbounded, a `1+1+…` chain built a tree deep enough to overflow the stack in the rewriter's own recursive walks. Exceeding a bound is a `SyntaxError` (Rewrite / Optimize / Materialize) or a failed CTE alias.
- **Request size.** `REWRITER_MAX_SQL_BYTES` (4 MiB; 0 disables) bounds the statement plus every `CommonTableExprRewrite` body: Rewrite answers `RewriteError` `query exceeds maximum supported size` before parsing. `REWRITER_MAX_ERROR_BYTES` (1 MiB) bounds RewriteErrorMessage's error text. The gRPC receive cap is derived from both plus 1 MiB (`REWRITER_MAX_RECV_MESSAGE_BYTES` overrides); the HTTP body cap is twice that (`REWRITER_MAX_HTTP_BODY_BYTES`, answered with 413 and the connection closed, since the rest of the body is not read).
- **Concurrency.** The gRPC sync server runs under a `ResourceQuota` of `REWRITER_MAX_SERVER_THREADS` (64, floor 2); past it calls fail fast with `RESOURCE_EXHAUSTED`.
- **RewriteErrorMessage.** Its passes ([src/error_message_rewrite.h](src/error_message_rewrite.h)) are linear scans, not `std::regex` (upstream traced its 2026-09-03 CPU saturation to per-mapping regex scans): KMP searches, a regex-equivalent matcher for table / database names, and the "position N" remap's Myers diff bounded to `kMaxOffsetMapEdits` (2048) edits, past which positions stay as ClickHouse printed them. All passes share one byte budget (`REWRITER_ERROR_SCAN_BUDGET`, 128 MiB) and the call's cancellation. An oversized request, a spent budget, a cancelled call, a re-run rewrite that does not succeed, or a result that still names this request's physical routing returns `Success` with a fixed text that names nothing (`error message withheld: <reason>` in `message`), never the raw ClickHouse text. The last check (fail closed, `hiddenNamesFor` in rewriter-server.cc) looks for the physical and protocol databases of the routing options (dynamic `database_map` values, `protected_databases`, the SI reserved and safe/unsafe databases; static `table_with_database_map` / `remote_table_map` databases) as case-sensitive whole identifiers, minus names the caller may write itself (logical names, non-protected known-physical databases), and for remote addresses, hosts and passwords as literals; `tests/error_redaction_test.cc` pins it. Replacement text is inserted literally (`std::regex_replace` read `$&` / `$1` in the caller's SQL as format escapes). `tests/dos_hardening_test.cc` pins the scans to the regexes they replaced.

### Dynamic construction — the policy in one place

The shared dynamic-mode logic lives in [handlers/name_rewrite.{h,cc}](src/handlers/name_rewrite.cc)'s `applyDynamicRewrite` — invoked by every non-SELECT single-target handler in dynamic-mode, and by SELECT's per-`ASTTableExpression` walker when SELECT falls back to dynamic. It resolves `(origin_db, origin_table)` + `dynamic_args` into `(physical_db, new_table)` as follows:

```
logical   := origin_db (SQL qualifier) OR dynamic_args.upstream_logical_database_in_context
physical  := dynamic_args.database_map[logical]
             OR logical  (if logical ∈ dynamic_args.known_physical_databases)
             OR reject with InvalidRewriteRequest
delim     := dynamic_args.delim ("_" by default)
new_table := logical + (delim + extra_arguments joined by delim, iff extras non-empty)
                     + "." + origin_table
```

**Storage-integrity surface (`dynamic_args.storage_integrity`, [handlers/storage_integrity.cc](src/handlers/storage_integrity.cc)):** SI lookup is a policy layer before ordinary dynamic resolution. A logical SI key is usable only when its logical database is present in the account-filtered `database_map`; `known_physical_databases` never grants access to a global logical SI key. Once authorized, SI mapping wins over ordinary/remote mapping and `is_remote` is forced false. SELECT-family roots (`SELECT`, `UNION`, `INTERSECT`, `EXCEPT`) replace each SI table expression with `(SELECT * EXCEPT (<reserved-rid>) FROM <safe> [UNION ALL SELECT * EXCEPT (<reserved-rid>) FROM <unsafe> WHERE _part NOT IN (...)]) AS <alias>`. EXISTS maps to the safe table; DESCRIBE emits the safe-table `system.columns` metadata SELECT. INSERT keeps the ordinary physical rewrite, but is authorized first and carries `is_storage_integrity=true` so the caller's signed ingress can decide admission. Every other SI-touching write, DDL, DCL, SHOW CREATE, or CREATE VIEW/MATERIALIZED VIEW body is rejected with `UnsupportedStatement` and the signed-lane message.

Every database used by a configured `safe_table` or `unsafe_table` is a protocol-owned namespace. Direct access is rejected across qualified and current-database table nodes, database-scope USE/SHOW/DDL/DCL, table-valued namespace functions (including remote/cluster/merge and local MergeTree inspection functions), `IN`/`GLOBAL IN` table RHS forms, namespace-bearing table engines, and local ClickHouse dictionary sources. Namespace arguments that cannot be resolved safely reject conservatively. CTAS/INSERT SELECT/view-body source trees run the same preflight. Any use of the reserved row-id as an SI-statement identifier or alias rejects; wrappers that the rewrite cannot preserve (`FINAL`, `SAMPLE`, `WITH OFFSET`, table alias column lists) reject only when bound to the actual SI table expression, leaving ordinary or mixed ordinary wrappers unchanged.

The Go/C++ behavioral contract lives in [tests/testdata/storage_integrity_cases.json](tests/testdata/storage_integrity_cases.json), byte-identical to `rewriter-go/internal/harness/testdata/storage_integrity_cases.json`. The frozen schema, exact-SQL comparison, local byte pins, and paired-copy procedure are documented under **Storage-integrity parity contract** below. Change both copies through paired PRs and run the Go harness with this server as `REWRITER_ORACLE_ADDR` before publishing either engine.

The trailing separator between the prefix and `origin_table` is **always** a literal `.` — it is NOT the configurable `delim`. The CH formatter wraps the resulting table name in backticks via `IdentifierQuotingRule::WhenNecessary` because it contains a dot, so callers see SQL like `` physical_db_1.`tenant1.events` ``. Examples (`delim="_"`):

| extras | original | result |
|---|---|---|
| `[]` | `tenant1.events` | `` physical_db_1.`tenant1.events` `` |
| `[]` | `events` (USE tenant1) | `` physical_db_1.`tenant1.events` `` |
| `["shard0"]` | `tenant1.events` | `` physical_db_1.`tenant1_shard0.events` `` |

The "extras block is optional" rule keeps an empty `extra_arguments` from producing a stray leading delim before the dot. `buildDynamicTablePrefix` (same file) is just `applyDynamicRewrite`'s construction with an empty `origin_table`, i.e. `logical + (delim + extras.join(delim) iff non-empty) + "."` — used by SHOW TABLES to filter / strip the prefix.

### Table-reference policy (housegate spec 2026-09-26)

The dynamic-mode policy that `preflightTableReferences` opens (step 2 above) mirrors rewriter-go's preflight. Its message texts are a byte-for-byte cross-engine contract (`kIdentifierParameterMessage`, `kUnsupportedStatementMessage` and the message helpers declared in [handlers/table_reference.h](src/handlers/table_reference.h)).

- **AST members outside `children`.** ClickHouse's parser keeps some subtrees only in a field. Every policy walker (T2 / T3 / T5 / T6 / R2, the SI checks, the system-table collector) and the rewrite walk iterate `children`, so a read there was invisible and unrewritten.
  - `registerFieldOnlyChildren` ([handlers/common.h](src/handlers/common.h)) adopts these fields as children right after parsing, for the request ([rewriter-server.cc](src/rewriter-server.cc)) and every CTE option body ([ASTTransformers.cc](src/ASTTransformers.cc)): `ASTWindowListElement::definition` (WINDOW), `ASTColumnsApplyTransformer::lambda` / `parameters` (APPLY), `ASTTTLElement::group_by_key` / `group_by_assignments` (TTL `GROUP BY … SET`) and `recompression_codec` (`RECOMPRESS CODEC`). Since ClickHouse 26.8 `ASTAlterCommand::refresh` (`MODIFY REFRESH … DEPENDS ON`) is held in `children` and deep-cloned, so it is no longer adopted. The formatter keeps reading the fields, which hold the same nodes. ENGINE arguments are already in `children` (R2 refuses a read there).
  - The list comes from the structural enumeration in the internal AST member enumeration research note: every AST-pointer member of ClickHouse's parser headers is listed, and every expression-capable member reachable from a statement the engine can answer Success for is probed with a marker read. Its recipe (`list_members.sh`, `enum_probe.cc`, `run_probe.sh`) and the results at the pinned submodule are committed beside it. **Re-run it whenever the `clickHouse` submodule moves**: a ClickHouse bump can add a member, and an unadopted one is invisible to every walker.
  - **Clone a parsed tree only through `clonePolicyAst`, before registration.** A registered tree's `clone()` would share adopted subtrees (APPLY's `clone()` copies `children` by pointer). Today the SI reject annotator's copy is the only such clone; the unresolved-name check walks in a check-only mode instead of cloning.
- **Name binding** ([handlers/cte_scope.h](src/handlers/cte_scope.h), a port of rewriter-go's `readSourceScope`). One `CTEAliasScope` drives the rewrite walk, the unresolved-name check, the SI read and namespace collectors, the system-table collector and the accessed-table collectors.
  - A read-query CTE name binds a one-part FROM / JOIN name and an IN operand in every nested scope.
  - A WITH expression alias binds an IN operand (never a FROM name) in every nested scope when its value is provably not a table reference (`withValueIsNotTableReference`: a literal, a scalar subquery, a plain call-syntax function, or an expression that names nothing). `if` / `ifNull` / `coalesce` / `CAST` and the other forms Polyglot types as their own node are not plain calls, so an identifier argument keeps the operand a table, as in rewriter-go. `multiIf` is treated the same way, deliberately stricter than rewriter-go, which binds it. Any other WITH alias binds nothing and shadows an enclosing binding of its name.
  - A projection alias binds an IN operand only in its own SELECT; a table-source alias never binds.
  - The leading SELECT's WITH reaches every later UNION / INTERSECT / EXCEPT arm (ClickHouse's `enable_global_with_statement` default).
  - Inside a stored view body (CREATE VIEW / MATERIALIZED VIEW, any depth) a WITH alias binds only a value the parser folds into one literal (a scalar, or a flat tuple / array of scalars), and no projection alias binds.
  - In an R2 position (structured DELETE / UPDATE, ALTER actions, INSERT VALUES rows, CREATE column / constraint / index / TTL / storage expressions) nothing binds, because ClickHouse qualifies every name with the current database there.
  - `view()`, `viewIfPermitted`, `viewExplain` and `executable()`'s query open a fresh scope.
  - A bound operand is left as written and unreported; every other one-part IN operand is a tenant table (T4).
- **Unqualified names that do not resolve.** In dynamic mode a one-part table name (FROM / JOIN, subquery, CTE body, set arm, `view()` body, IN operand) that no scope binds, that is not an SI table, and that `applyDynamicRewrite` cannot resolve (empty or unmapped logical context, or a logical database mapped to a missing remote upstream) is refused with `unqualified table "<t>" does not resolve through the session's logical database`: `InvalidRewriteRequest` in a SELECT or view body, `UnsupportedStatement` in an INSERT … SELECT / CTAS body. `rejectUnresolvedUnqualifiedTable` ([handlers/select.cc](src/handlers/select.cc)) runs after every other check of the walk and before the rewrite, names the first such table in AST order, and clears `table_rewrites` (the write statement's own target entries included). A qualified name whose database resolves to nothing is still left as written.
- **Settings (R5).** The settings token scan and the AST check every query-level SETTINGS clause (subqueries, view / MV bodies, the INSERT header, CTAS, the command tails of DESCRIBE / SHOW / EXISTS / ALTER / DELETE / UPDATE / DROP), CREATE storage SETTINGS and a session `SET`.
  - **Refused names** — `UnsupportedStatement` `table setting <name> is not accepted`, for any value and in any case:
    - SQL-bearing and dialect settings: `additional_table_filters`, `additional_result_filter`, `parallel_replicas_custom_key`, `dialect`, `*_dialect`;
    - name-binding settings: `enable_global_with_statement`, `compatibility`, `implicit_table_at_top_level`, `promql_table`, `promql_database`;
    - settings a ClickHouse 26.8 server honours (refused whatever the embedded parser, since the backend decides): the query-construction settings `select`, `filter`, `order`, `sort` (SQL text the server wraps around the query) and `database` (the current database, like USE); the format overrides `format`, `input_format`, `output_format`, `default_format` (`input_format` would re-read an INSERT's opaque inline data as Values); `asterisk_include_virtual_columns`; `s3_allow_server_credentials_in_user_queries` and `dynamic_disk_allow_*`; `url_base`, `s3_base`; `analyzer_compatibility_allow_cte_redefinition`, `analyzer_compatibility_prefer_alias_over_subcolumn`, `analyzer_compatibility_multiple_joins_qualify_column_names`, `analyzer_inline_views`; `enable_streaming_queries`; `ai_function_text_default_credentials`, `ai_function_embedding_default_credentials`;
    - old-analyzer settings: `legacy_column_name_of_tuple_literal`, `profile`; and `enable_analyzer` / `allow_experimental_analyzer` unless the value is one unsigned token whose raw lexeme is `1`, `true`, `'1'` or `'true'` (any case) followed by a clause boundary (`0x1`, `+1`, `1.0`, `1e0`, `x'31'`, `$$true$$`, expressions and parameters are refused).
  - **The analyzer must stay on.** The binding rules assume the new analyzer: under `enable_analyzer = 0` a projection `EXISTS(…) AS name` alias, a `tuple(…)` WITH alias with `legacy_column_name_of_tuple_literal = 1`, or an `if(…)` value folded to an identifier turn a bound operand into a table read. **HouseGate must refuse the same settings in the native Query packet, and every deployment's server and user profiles must keep the analyzer on**: a setting applied outside the SQL text is invisible to this engine.
  - **Table-setting keys.** `ALTER … MODIFY / RESET SETTING` keys are table settings: the names above stay admitted there, as in rewriter-go (MergeTree has no such setting and ClickHouse answers UNKNOWN_SETTING), while `disk` / `storage_policy` are refused.
  - **`statement is not supported`** answers:
    - a setting value that is not a plain numeric, string or boolean literal, a negative hex / binary / inf / nan, and in a session SET or command tail any hex / binary literal or signed inf / nan;
    - a compound (dotted) setting name in a query-level list or SET (in a table-setting key, the table-setting message when its last part is refused);
    - a quoted setting name whose source spelling is not its plain text (a backslash, a doubled quote, Unicode quotes) after a SETTINGS / SETTING keyword, in the statement-initial SET list or in a RESET SETTING key list — unless it decodes to a refused name, which gets the table-setting message (ClickHouse reads `` `\Nenable_global_with_statement` `` as that setting);
    - the boolean shorthand `SET name` with no `=`.
  - **No verbatim settings path.** The engine formats every statement from the AST; DESCRIBE and SHOW COLUMNS / INDEX / DICTIONARIES are echoed exactly as parsed and checked, and the INSERT data tail is scanned as well. A SETTINGS list ClickHouse's parser cannot parse is a SyntaxError, and a text the scan cannot tokenize fails closed. HouseGate's own `SQL_x_*` / `SQL_sentio_*` keys stay accepted.
- **System tables** ([handlers/system_tables.{h,cc}](src/handlers/system_tables.cc), step 1 of the spec's "The system database", ported from rewriter-go #58). Every tenant reaches ClickHouse as one shared user, so ClickHouse's per-user filtering of `system.*` separates nothing.
  - **Allowlist.** In dynamic mode, in both SI states, caller SQL may name only 45 tables of database `system` (exact, case-sensitive): 33 static or server-global ones (`one`, `numbers`, `functions`, `settings`, `formats`, …), `clusters`, and 11 per-database metadata tables the Sentio driver reads (`tables`, `columns`, `data_skipping_indices`, `projections`, `parts`, `parts_columns`, `projection_parts`, `projection_parts_columns`, `databases`, `completions`, `mutations`). Any other one, including a table a future ClickHouse adds, is `UnsupportedStatement` `system table system.<t> is not accessible`, with only `system.<t>` recorded as accessed.
  - **Collector order.** `collectObjectRefs` reads every caller-input reference, and the first refused one names the refusal:
    1. the qualified runs of a command statement's text (DESCRIBE, EXISTS, SHOW, RENAME / EXCHANGE, GRANT / REVOKE, USE, an ALTER with an UPDATE action);
    2. write / DDL targets;
    3. read sources and carriers in walker order (IN operands, table-function and table-engine arguments, VALUES rows and the adopted out-of-`children` members included; an unqualified name resolves in the session database unless a scope binds it);
    4. the opaque texts of a structured statement;
    5. string-lookup arguments.

    Names are decoded as ClickHouse's ParserIdentifier decodes them (a name still holding a backslash is decoded again, erring toward refusal); the rewriter's own `system.tables` / `system.columns` synthesis is never a reference.
  - **Precedence.** Right after T3, before T5 / T6 / R5 / R2 and the handlers. While the SI surface is active and the statement also names an SI object, the preflight defers the refusal (`deferred_system_table`) and `doRewrite` applies it to the SI pipeline's would-be Success (`rejectDeferredSystemTable`), so an SI message wins. A text that cannot be tokenized fails closed.
  - **SHOW mapping.** SHOW DICTIONARIES / MERGES / FILESYSTEM CACHES are refused as `system.dictionaries` / `system.merges` / `system.filesystem_cache_settings`, after their SI namespace check, R7 and R5. In `handleShowSystemFormQuery`, R5 runs first; then:
    - SHOW CREATE of an access entity and DESCRIBE FILESYSTEM CACHE are `statement is not supported` in both SI states;
    - a kind that reads a refused system table (PROCESSLIST, USERS, ACCESS, …) is refused with its table in both states, except CURRENT / ENABLED, which the SI catch-all answers while the surface is active;
    - FUNCTIONS and ENGINES pass in both states; SETTING and PRIVILEGES pass only while the surface is inactive (the SI catch-all answers them while it is active);
    - an unknown kind, or a text the lexer cannot tokenize, is `statement is not supported`, or the SI catch-all while the surface is active.
  - **Known residual (step 2, [housegate/housegate#218](https://github.com/housegate/housegate/issues/218)).** The 11 metadata tables still show every tenant's names (and `parts*` partition values, `mutations` command text); step 2 serves them through a filtered logical rewrite.
- **Fidelity refusals.** Every accepted statement is re-emitted from ClickHouse's AST, so a spelling the embedded 26.8 parser normalises into SQL that a supported server (25.8, 26.2) reads differently, or a clause a synthetic output would drop, is refused with `UnsupportedStatement` `statement is not supported` instead of being silently changed:
  - synthetic SHOW TABLES / SHOW DATABASES and the SI DESCRIBE metadata SELECT refuse the clauses they would drop (the SHOW and DESCRIBE handler bullets above);
  - N1: a literal tuple inside an extra pair of grouping parentheses (`((1, 2))`, `((1, 2) AS x)`, `[((1, 2))]`, `x IN ((1, 0, '0'))`), which 25.8 / 26.2 read as `Tuple(Tuple(…))` while the parser folds it to `(1, 2)`, is **preserved**, not refused (Sentio driver gap 2): `planLiteralFolds` finds each group in the source, the text is parsed again with a marker call before each group's outer `(` (`markLiteralFolds`), and `adoptLiteralFolds` accepts the marked tree only when, each marker replaced by its tuple, it hashes like the source's tree (both as clones), then renames each marker to ClickHouse's nameless function, which the formatter prints as `((1, 2))`. The output may gain or lose the formatter's own outer priority parentheses (`(((1, 2)))` → `((1, 2))`, `((1, 2)).1` → `(((1, 2))).1`); input and output were measured equal (type and value, or error code) on 25.8, 26.2 and 26.3. A group the marked parse cannot take (`DROP PARTITION ((1, 2))`), one whose marked tree differs (a fold beside other tuple elements, `(((1, 2)), 3)`, where the parser merges the literals), a group right after `NOT` (`NOT ((1, 2)) = …`: `NOT (` is a call to 25.8 / 26.2 and an operator to 26.3), more than `kMaxLiteralFolds` (10 000) groups in one statement, and a source spelling the marker `__housegate_grouped_literal_tuple` stay refused. A `(` counts as a call's own parenthesis only after a non-keyword word naming a call in the tree, and a `(` opening one set of a `GROUPING SETS` list is syntax too (`GROUPING SETS (((1, 2)))` is re-emitted as written); a misread is caught by the tree comparison. A group is a literal tuple only when every nested round-bracket group is one in turn and no sign precedes a bracket (measured on 25.8 / 26.2 / 26.3: `(2)`, `(-2)`, `('a')`, `((2))`, `(2, 3,)`, `()`, `+(1)` make the tuple an expression there); a sign keeps it literal only before a number or `inf` / `infinity` / `nan` (`((1, +'a'))`, `((+NULL, 1))` are expressions there); a group of literal-tuple shape that fails this (`((1, (2)))`, `((+(1), 2))`, `((1, +'a'))`) is refused, because the embedded parser would still fold it into a literal and the preserved grouping would change its meaning on 25.8 / 26.2. Literal elements are numbers, strings, `x'…'` / `b'…'`, heredocs, NULL / TRUE / FALSE / inf / nan and nested literal tuples, measured on 25.8 / 26.2; a server that accepts more literal spellings needs `literalTupleToken` extended;
  - `NOT (expr)` followed by an operator or postfix (`NOT (a) = 1`, `NOT (a) IN (1)`, `NOT (a) IS NULL`, `NOT (p).1`, `NOT (a) - 1`): 25.8 / 26.2 read `NOT (` as a call, `not(a) = 1`, while the embedded parser reads an operator and re-emits `NOT (a = 1)` (measured: rows, types or errors change on 25.8 / 26.2; 26.3 agrees with the output). `notCallPrecedenceDiverges` refuses it unless what follows the group ends the expression (a closing bracket, `,`, `;`, `?`, `:`, a quoted alias, AND / OR, AS, THEN / ELSE / END / WHEN, ASC / DESC, WITH or a clause keyword); a bare-word implicit alias and `::` are refused conservatively. Unary minus (`-(a) = -1`, `-(p).1`) reads the same on all three servers;
  - N2: a float literal at or below `DBL_MIN` (one that underflows, a subnormal, or one that rounds to `DBL_MIN`, its own spelling included), which 25.8 rejects while the formatter re-emits a value it may accept;
  - a lambda holding a query or an IN (preflight, first), and a lookup-family `APPLY` transformer (T6);
  - a parametrised alias (preflight);
  - a column declaration's own `SETTINGS (…)` in a CREATE column list or `ALTER … ADD COLUMN` (`ALTER … MODIFY COLUMN … SETTINGS` and table-level SETTINGS stay admitted);
  - a nested `(EXPLAIN …)` in an expression position and a subquery in a CODEC argument, data-type parameter or storage-setting value already fail closed (a SyntaxError, a T5 / T3 refusal or `statement is not supported`), pinned in `TableRefFidelity.ExplainAndTypeArgReadsAreRefused`.

  `planLiteralFolds` (N1 / N2) reads the source text up to an INSERT's inline data, fails closed on text it cannot tokenize or bracket-match, and applies in every mode, not only dynamic.
- **After the handlers.** `doRewrite` ([rewriter-server.cc](src/rewriter-server.cc)) decides these on the parse tree before any handler mutates it and applies them only to a would-be Success, in dynamic mode (the literal-fold refusal in every mode), in this order:
  1. R5 while the SI surface is active (statements the SI handlers accept without a settings hook of their own);
  2. `inOperandInUnrewrittenPosition`: a table-naming IN operand or read in an ALTER action, a structured DELETE / UPDATE or a CREATE outside its SELECT body (defence in depth behind R2, and the only guard of an IN operand inside a CREATE's `AS <table function>` source);
  3. the deferred system-table refusal;
  4. column-declaration SETTINGS;
  5. the literal-fold refusal;
  6. a deployment-identity call (`firstDeploymentIdentityCall`, [handlers/table_reference.h](src/handlers/table_reference.h); dynamic mode only, both SI states): a bare word or quoted identifier directly followed by `(` and not after `.`, case-insensitively one of `currentDatabase`, `database`, `schema`, `current_database`, `currentSchemas`, `current_schemas`, `currentUser`, `user`, `current_user`, `session_user`, `authenticatedUser`, `authUser`, `hostName`, `FQDN`, `fullHostName`, `serverUUID`, `getMacro` (ClickHouse 26.3's names and aliases) or `pgGetUserById`, `pg_get_userbyid`, `currentRequestURL`, `currentHandler` (added in 26.8), or else an unqualified bare `currentDatabase`, `current_database`, `currentUser` or `current_user` identifier in the parse tree (`firstBareDeploymentIdentityName`, read before the handlers: the analyzer resolves these as the function when no column or alias of that name is in scope), is `UnsupportedStatement` `function <name> is not accessible` (the name as written, a quoted one decoded); after it, a `_database` column in the parse tree (bare or qualified; ClickHouse 26.8 gives MergeTree, Memory, Log, View, MaterializedView and system tables this virtual column holding the physical database) is `UnsupportedStatement` `virtual column _database is not accessible` (`firstDeploymentIdentityColumn`; C++ only, stricter than rewriter-go). A bare `user`, `DATABASE` or `SCHEMA` resolves the same way but is an ordinary column name and is left alone, a known residual. They name the shared deployment (the physical session database, the one ClickHouse user every tenant shares, the host), not the tenant's view of it. `version()`, `displayName()` and `timezone()` stay allowed: the ServerHello housegate relays carries them. rewriter-go applies the same rule last in `finalize` (`engine.FirstDeploymentIdentityCall`); `tests/metadata_access_test.cc` pins it and the upstream metadata corpus.

  Each clears the response's rewrite maps and accessed tables and echoes the SQL, except the deferred system-table refusal, which keeps the SI pipeline's accessed entries and adds the system table.
- **Parity with rewriter-go.** The shared corpus pins every common answer (see **Storage-integrity parity contract**). Every remaining difference measured against rewriter-go during the hardening work falls into one of these categories; this summary is the maintained record (the per-item measurement notes were working material and are not kept in the repository):
  1. **Go-local gate refusals.** rewriter-go's Polyglot parse / mid-statement-drop / regeneration gates refuse shapes C++ admits and that read no table: benign command tails (SETTINGS / FORMAT / INTO OUTFILE), canonical formatter forms such as `<=>` or `NO DELAY`, `DROP … IF EMPTY`, `TRUNCATE` without TABLE.
  2. **C++ SyntaxErrors.** ClickHouse's parser rejects text Polyglot accepts: `#c`, `U&'…'`, `.5`, a 3+-part `system.a.b.c`.
  3. **Message-only differences** on shared refusals: `logical db X not in database_map …` against `<KIND> target references logical database …`, the order of SI messages, T5 against T7 inside ALTER actions.
  4. **C++ deliberately stricter (fail closed):** N2 folds and the few N1 groups C++ cannot preserve (above), which Go keeps verbatim, escaped or dotted setting names, a parametrised projection alias, a `multiIf` WITH alias that Go binds.
  5. **C++ admits, Go refuses**, each measured read-free: GRANT / REVOKE with a `'*'` or several targets, `CREATE VIEW … DEFINER … SQL SECURITY DEFINER`, analyzer-on spellings such as the `SETTINGS enable_analyzer` shorthand, `= /*c*/ 1` and upper-case names ClickHouse rejects as unknown.

  The Go-side gaps found along the way (ENGINE-argument reads, ordinary `MODIFY REFRESH … DEPENDS ON` targets, nested EXPLAIN, the old analyzer) are closed in rewriter-go v0.16.0, whose corpus pins them.

### AST transformers ([src/ASTTransformers.cc](src/ASTTransformers.cc), [src/ASTTransformers.h](src/ASTTransformers.h))

Each transformer subclasses `IASTTransformer` (itself an `IAST` so it can live in the tree during debugging). They mutate the AST in place:

- `ASTReplaceTransformer` — SELECT-tree table rewrites. Walks `ASTTableExpression` nodes and dispatches to `planTableRewrite()` for every `ASTTableIdentifier` it finds. Three map kinds in precedence order: `table_name_map` (plain rename) → `remote_table_map` (swap the identifier for a `remote('addr', db, table, user, password)` function call) → `table_with_database_map` (attach an explicit database). Every match gets recorded in `transformer.rewrites` so the SELECT handler can surface it on the response.
- `ASTRewriteCTETransformer` — injects named CTEs into `WITH` clauses of every `SELECT` subquery that actually references them. See `parseCTEMapToAST` (parses each CTE SQL once, tolerant of individual failures) and `collectCTEKeysForSelect`.

`planTableRewrite()` is the SELECT-path primitive. Given `(origin_name, three maps)` it returns a `TableRewritePlan { kind, db, table, remote }`. Only `ASTReplaceTransformer` consumes it; non-SELECT handlers use `applyDynamicRewrite` (see "Dynamic construction" above) instead — the two paths don't share logic by design.

`LimitRewrite` / `OffsetRewrite` / `SettingsRewrite` used to have their own transformer classes but are now applied inline in [handlers/select.cc](src/handlers/select.cc) — all three batch into a `PendingSelectTransforms` struct and flush in a single AST walk.

`response.original_accessed_tables` is populated by every table-targeting handler:

- **SELECT** uses `collectAccessedTablePairsFromAST` (private to [handlers/select.cc](src/handlers/select.cc)) to walk pre-rewrite ASTs (main SQL + each CTE body), skipping names its `CTEAliasScope` binds (see **Table-reference policy**) and erasing externally-supplied CTE alias entries before re-walking their bodies. `rewriteEmbeddedBody` does the same for INSERT … SELECT, CTAS and view bodies, which report their sources after the write target. Each remaining pair runs through `resolveAccessedTable` ([handlers/name_rewrite.cc](src/handlers/name_rewrite.cc)) to fill in `logical_database` / `physical_database` / `is_remote`.
- **Non-SELECT table-targeting handlers** (writes / EXISTS / SHOW CREATE / DESCRIBE) call `recordAccessedTable` (also in [handlers/name_rewrite.cc](src/handlers/name_rewrite.cc)) once per `(db, table)` target processed by `rewriteOneTarget` (in writes.cc) or its inline equivalents. RENAME records both `from` and `to`; `CREATE TABLE x AS source` records target plus source.
- **CREATE DATABASE / DROP DATABASE** call `recordAccessedDatabase` ([handlers/name_rewrite.cc](src/handlers/name_rewrite.cc)) — emits one db-level entry with `original_table` empty, `logical_database` = target db, and `physical_database` resolved via `database_map` when possible (typical for DROP, typically empty for CREATE). Callers branch on `original_table.empty()` to tell db-level entries apart from table-level ones.
- USE / SHOW TABLES / SHOW DATABASES normally do not populate the field — they're pure DB rewrites surfaced via `database_rewrites`. A reject against a protocol-owned SI physical database is the exception: it records a database-shaped SI entry (`original_table=""`) before returning.
- The recording happens before any reject path, so a partial list may appear on rejected (non-Success) responses.

### Protocol

The pinned
[`rewriter-proto`](third_party/rewriter-proto/proto/rewriter.proto) submodule
defines the contract. Key invariants worth preserving:

- `RewriteOp` + `RewriteOption.value` are a tagged-union by `op` — adding a new op means: new enum value, new `*Args` message, new `oneof` case, new `case` in the dispatch switch, and probably new response fields. Bump both C++ and Go clients.
- `TableNameRewrite` is the only table-touching op. Its `RewriteTableNameArgs` has two sub-messages:
  - `static_args` (`RewriteTableStaticArgs`) — the three maps (`table_map`, `remote_table_map`, `table_with_database_map`) in lookup-precedence order; when set, every table-targeting handler uses static mode (the unified static→dynamic precedence in step 3).
  - `dynamic_args` (`RewriteTableDynamicArgs`) — used when `static_args` is absent, and directly by the database-level handlers: `database_map` (logical → physical), `known_physical_databases` (logical that's already physical → passthrough), `upstream_logical_database_in_context` (default logical for unqualified SQL), `delim` (default `"_"`), `extra_arguments` (repeated, joined by `delim`), `upstream_physical_database_in_context`, `logical_database_to_remote_upstream_index` / `remote_upstreams` (remote-mapped logicals), `protected_databases` (databases T3 refuses in every position, each a simple identifier) and `storage_integrity` (`StorageIntegrityArgs`, the SI surface). Dynamic mode is what activates the table-reference policy.
- Response `statement_type` is a `StatementType` enum (`STATEMENT_TYPE_SELECT`, `_USE`, `_SHOW_TABLES`, `_SHOW_CREATE_TABLE`, `_EXISTS_TABLE`, `_CREATE_TABLE`, `_DROP_TABLE`, `_ALTER_TABLE`, `_RENAME_TABLE`, `_INSERT`, `_UPDATE`, `_DELETE`, `_CREATE_DATABASE`, `_SHOW_DATABASES`, `_DROP_DATABASE`, `_TRUNCATE_TABLE`, `_GRANT`, `_REVOKE`, `_CREATE_VIEW`, `_CREATE_MATERIALIZED_VIEW`, `_DROP_VIEW`). `STATEMENT_TYPE_UNSPECIFIED` (= 0) is the default when classification didn't run (parse errors, etc.). Adding new values is fine; renumbering or reusing numbers is not.
- `RewriteCode` splits rejection taxonomy into four cases — callers should branch on this, not on `message` strings:
  - `Success` (0): accepted.
  - `SyntaxError` (1): ClickHouse's `ParserQuery` rejected the SQL text; `message` carries the parser's `displayText()`.
  - `RewriteError` (2): generic bucket kept for unexpected rewrite failures. Prefer the more specific codes below when classifying new reject paths.
  - `UnsupportedStatement` (3): the SQL is valid but the rewriter doesn't handle this statement kind / variant (CREATE LIVE/WINDOW VIEW, CREATE DICTIONARY, TRUNCATE VIEW, DROP DICTIONARY, TRUNCATE DATABASE, OPTIMIZE, RENAME DATABASE, EXISTS VIEW/DATABASE/DICTIONARY, SHOW CREATE VIEW/DATABASE/DICTIONARY, INSERT INTO FUNCTION, multi-table DROP/TRUNCATE, ALTER cross-table partition refs, KILL/BACKUP/...). Also: CREATE/DROP DATABASE without a `dynamic_args` option (we won't ship the raw DDL to the physical DB without policy context). Also: GRANT/REVOKE variants the privilege-delta path doesn't model (`ON *.*`, role-membership grants, column-level grants, `WITH REPLACE OPTION`, `REVOKE FROM ALL`/`ALL EXCEPT`, `GRANT CURRENT GRANTS`, `ATTACH GRANT`, or any GRANT/REVOKE without `dynamic_args`). Legacy callers may pass through only when no active SI contract/classification is involved; acknowledged SI callers must fail closed on every non-Success response.
  - `InvalidRewriteRequest` (4): the caller's `RewriteOption` can't be applied — their rewrite config is wrong for the SQL they sent. Callers MUST NOT pass through; surface the error. Non-SELECT cases: the logical DB resolves to no physical (not in `database_map`, not in `known_physical_databases`), or the target is unqualified and `upstream_logical_database_in_context` is empty.
- Top-level `response.table_rewrites: map<string, string>` records TABLE rewrites only — keys/values formatted as `"db.table"` (or bare `"table"` when no db was present). Populated by SELECT, writes, EXISTS, SHOW CREATE, RENAME. For SELECT `remote_table_map` hits, the value is the remote-side `db.table`; the full `remote('addr', …)` call lives in `sql_after_rewrite`.
- Top-level `response.database_rewrites: map<string, string>` records DB-level rewrites only — keys are the original logical DB, values are the resolved physical DB. Populated by USE and SHOW TABLES (the two statement kinds whose rewrite is purely at the database level). Kept separate from `table_rewrites` so callers can branch on "did the DB change?" vs "did a table change?" without parsing key formats.
- Both maps omit no-op entries (origin == rewritten).
- `RewriteSQLResponse` is flat — no `extra_value` oneof, no `{use,show,write}_stmt_value` messages. Everything a caller needs for routing lives in `statement_type`, `code`, `message`, `sql_after_rewrite`, `original_accessed_tables` (structured `AccessedTable` records: `original_database` / `original_table` / `logical_database` / `physical_database` / `is_remote` / `is_storage_integrity`), `table_rewrites`, `database_rewrites`, `failed_cte_aliases`, `privileges_deltas` (structured `PrivilegeDelta` records emitted only by GRANT/REVOKE — action / scope / original+logical+physical db / original+physical table / privilege keyword list / grantees / `grant_option`), `existence_clause` (an `ExistenceClause` enum — `IF_NOT_EXISTS` for a CREATE that carried `IF NOT EXISTS`, `IF_EXISTS` for a DROP/TRUNCATE that carried `IF EXISTS`, `UNSPECIFIED` otherwise; set from the parsed AST before dispatch, so accurate even on a rejected response — only `SyntaxError` leaves it `UNSPECIFIED`), and `storage_integrity_contract_version` (the positive v1/v2 enforcement proof). Field tag 4 (the legacy flat `original_accessed_table_names`) is `reserved`.
- Syntactic / semantic rewrite failures return `Status::OK` with a non-Success `RewriteCode`; only unexpected server errors would return a gRPC error.

### `Optimize` RPC

A second top-level RPC, separate from `Rewrite`. Lives in `RewriterServiceImpl::doOptimize` / `Optimize` in [src/rewriter-server.cc](src/rewriter-server.cc) and is routed by [src/rewriter-http-server.cc](src/rewriter-http-server.cc) at `POST /optimize` (also accepts `/rewriter.RewriterService/Optimize`).

- **What it does**: currently, JOIN left/right swap based on caller-supplied physical-table sizes, applied only to SELECT queries. Skip rules match ClickHouse's own `optimizeJoin.cpp` policy (ASOF, PASTE, USING, SEMI/ANTI strictness are left alone — see [src/handlers/join_swap.h](src/handlers/join_swap.h)).
- **Why separate from `Rewrite`**:
  1. *Table-size key disambiguation* — by the time `Optimize` is called, the SQL has already been through `Rewrite`, so every table identifier in the SQL is a physical one. `OptimizeRequest.table_sizes` keys are unambiguously `<physical_db>.<physical_table>` (or bare `<physical_table>` when the SQL is unqualified). Callers populate them by reading `system.tables` / `system.parts` after `Rewrite`, using the response's `original_accessed_tables` field to discover which physical tables to look up. (Inside `Rewrite`, callers could not tell whether a size key was supposed to be logical or physical — the request hadn't been resolved yet.)
  2. *Rewrite ≠ optimize* — one fixes semantics (logical → physical, multi-tenant prefix translation, etc.), the other tunes performance. Different lifecycle, different failure modes; keeping them in one RPC was muddling the contract.
  3. *Best-effort optimization with clean fallback* — `Optimize` is fire-and-forget: any failure path (parse error, no JOIN, ASOF/PASTE/etc. skip rule) returns `sql_after_optimize == request.sql` with a non-OK `OptimizeCode`. Callers can always run `sql_after_optimize` regardless of code; the code is for observability, not for branching fallback.
- **Failure semantics**:
  - `OptimizeOK` (0): a JOIN was swapped. `swap_applied = true`.
  - `OptimizeSyntaxError` (1): `ParserQuery` rejected the SQL. `sql_after_optimize` echoes the input.
  - `OptimizeUnoptimizable` (2): SQL parsed but had nothing to swap (single table, non-SELECT, JOIN that hits a skip rule, sizes don't justify a swap, etc.). Not an error — callers proceed with the original SQL.
- **`forceGlobalForRemoteAsymmetry`**: `Optimize` does NOT re-run this pass. The pass already ran inside `Rewrite` and JOIN swap doesn't introduce new remote/local asymmetries (it only reorders existing ones), so the GLOBAL markers placed by `Rewrite` remain correct.
- **Why a separate RPC rather than `query_plan_join_swap_table` on ClickHouse**: CH's own optimizer's `estimateReadRowsCount` recognises only `ReadFromMergeTree` / `ReadFromMemoryStorageStep` — anything else (notably `ReadFromRemote` / `ReadFromCluster`) returns `nullopt`, and the auto-mode decision requires both sides to estimate. For SQL that involves `remote()` / `cluster()` table functions, CH's swap is a no-op. The proxy layer that calls this rewriter has out-of-band knowledge of remote-shard sizes that CH cannot see locally, so this RPC is the only place that swap decision can be made for our workload.

### `MaterializeSQL` RPC

A third top-level RPC, separate from `Rewrite`. The **Phase-1 signing normalizer** — it runs at the trusted agent/SDK *before* a `StatementEnvelopeV2` is signed (vs `Rewrite`, the runtime physical-name rewrite that runs after ingress). It rewrites non-deterministic ClickHouse functions in the SQL text to deterministic literal expressions, so the signed SQL hashes reproducibly and every replay executor computes the same result. Wire-compatible with the Go service ([housegate/rewriter-go#17](https://github.com/housegate/rewriter-go/pull/17)) so either service can be the materializer. Lives in `RewriterServiceImpl::doMaterializeSQL` / `MaterializeSQL` in [src/rewriter-server.cc](src/rewriter-server.cc) delegating to `rewriter_handlers::materialize` in [src/handlers/materialize.cc](src/handlers/materialize.cc); routed by [src/rewriter-http-server.cc](src/rewriter-http-server.cc) at `POST /materialize` (also `/rewriter.RewriterService/MaterializeSQL`).

- **Reads no clock / no RNG.** Every value comes from `MaterializeSQLRequest.inputs` (`MaterializationInputs`): `now_unix_ns` (optional int64), `random_uint64_values`, `random_float64_values`, `uuid_values` (all repeated, consumed positionally in left-to-right traversal order). The rewriter is a pure function of `(sql, inputs, policy)`.
- **Policy** (`MaterializationPolicy`): `profile_id` empty or `"sentio-p1-nondet-v1"` (the default) only; `timezone` empty or `"UTC"` (case-insensitive) only — else `MaterializeInvalidRequest`. The resolved profile is echoed in `materializer_profile_id` (default even on a policy reject, mirroring Go).
- **Mechanism** ([handlers/materialize.cc](src/handlers/materialize.cc)): parse with `ParserQuery`; a `Materializer` walks the AST pre-order and replaces each `ASTFunction` whose lowercased name is in the Go-mirrored `isKnownNondeterministic` set with a constructed literal/`toX(...)` AST node, recording a `MaterializedReplacement` (function_name / 0-based ordinal / literal_sql = `formatAst(node)` / value_type). `INSERT … VALUES` is special: ClickHouse leaves the VALUES payload off-AST as raw bytes (`insert->format == "Values"`), so `materializeValuesData` tokenizes it with `DB::Lexer` to split top-level `(...)` rows, parses each row's columns with `ParserExpressionList`, runs the **same** `Materializer` (cursors/ordinals continue), and re-emits — output is `formatAst(prelude) + tail` (`INSERT INTO t FORMAT Values(...)`, ClickHouse's own no-space round-trip form).
- **Supported functions** → literal: now/current_timestamp()/localtimestamp/localtime/nowInBlock → `toDateTime(s)`; utctimestamp/utc_timestamp → `toDateTime(s,'UTC')`; now64/nowInBlock64 → `fromUnixTimestamp64Milli(ms)`; today/current_date/curdate → `toDate(toDateTime(s))`; yesterday → `toDate(toDateTime(s-86400))`; rand/rand32/randConstant → `<n>` (UInt32, overflow-checked); rand64/random → `<n>` (UInt64); randCanonical → `toFloat64(x)` (finite, [0,1)); generateUUIDv4/**generateUUIDv7** → `toUUID('<lowercased>')`. `s = now_unix_ns/1e9`, `ms = now_unix_ns/1e6` (integer). The C++ extensions beyond Go's set — `generateUUIDv7`, `nowInBlock`, `nowInBlock64`, `randConstant` — reuse existing input channels (no proto change); Go rejects `generateUUIDv7`, so the two materializers diverge on what they *accept* (acceptable: materialization runs once at signing).
- **ClickHouse divergence from Go/polyglot**: bare SQL-standard keywords without parens (`CURRENT_TIMESTAMP`, `CURRENT_DATE`, `localtime`, `localtimestamp`) parse as **identifiers** in ClickHouse and error as `UNKNOWN_IDENTIFIER` at execution — they are *not* volatile, so the materializer correctly leaves them untouched. Only the parens forms (`current_timestamp()`, an alias of `now`) are `ASTFunction`s and get materialized.
- **Fail closed** (`MaterializeCode`): `MaterializeSuccess` (0); `MaterializeSyntaxError` (1, `ParserQuery` rejected); `MaterializeUnsupportedStatement` (2, a known volatile not in the supported set — e.g. `generateSnowflakeID`, `randNormal` — or a supported function carrying arguments like `now('UTC')`); `MaterializeInvalidRequest` (3, bad policy, or a supported function whose input channel is missing/exhausted/invalid — UInt32 overflow, float ∉ [0,1), malformed UUID); `MaterializeError` (4, internal/format failure, or an unparseable VALUES data section). On **every** non-Success path — and when zero replacements were applied — `sql_after_materialization == sql` (the original, echoed verbatim, no re-canonicalization).
- **Out of scope** (matching Go#17): `_hg_row_id` payload injection (operates on payload rows, not SQL text); distribution samplers / string generators (would need new input channels).

`Build & test (build box)` context from the GitHub Actions app (app ID `15368`;
